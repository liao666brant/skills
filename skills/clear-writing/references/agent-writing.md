# Agent 文档

用于面向 Agent 的文档，包括 Skill、AGENTS.md、CLAUDE.md，以及通过指针加载的执行说明和纯参考资料。目标是让 Agent 稳定使用资料、遵循过程，不是每次生成相同结果。纯参考资料不强加步骤，含执行动作时才核对步骤完成条件。

## 上下文指针

上下文指针命名尚未加载的材料，并说明何时读取；Skill 的 description 和 AGENTS 中的引用行都属于指针。必要材料未被读取时，先强化触发措辞，仍不可靠才考虑内联。

把能识别任务的引导词放在前面，说明材料用途并保留真正独立的触发分支。同义表达合并，每个分支只写一个触发条件；删除正文已表达的身份信息。指针常驻上下文，应比正文更严格地删减。

区分两种成本：

- 上下文负载是常驻内容消耗的 token 与注意力。移到指针后的正文不再常驻，但指针本身仍有成本。
- 认知负载是人需要记住文档及其使用时机的成本。没有指针的材料完全依赖人的记忆；在人类判断重要处保留这种责任，其他位置减少不必要的记忆负担。

## 信息层级与共置

步骤是按顺序执行的动作，参考是按需查询的定义、规则与事实，可以组合使用。文件内步骤是主层级；相关文件内参考次之；只有部分分支需要的详细材料放到条件指针之后。同层出现多条规则本身不是问题。

所有分支都需要的约束留在入口。披露太少会让参考掩埋步骤，披露太多会隐藏执行所需材料；依据分支选择层级，不能只按行数拆分。即使每行都有效，过量内容也会稀释注意力。

同一概念的定义、规则和例外放在一起。既删除多处重复的含义，也避免把一个含义拆散在不同位置。拆分会增加指针或人的记忆负担，只有收益能覆盖成本时才拆。

## 步骤与完成条件

每个步骤结束时应能判断完成与否，同时保持要求强度。“已经理解”缺乏可观察边界；“覆盖每个修改端点的成功与错误响应”不能压缩成“测试一下”。平铺参考中的“应用每条规则”也有覆盖要求，不能靠生成清单代替执行。

出现提前结束时先收紧完成边界。只有边界无法再明确，且真实运行确有后续步骤诱发抢跑，才考虑按顺序隐藏后续步骤。隐藏须跨越真实上下文边界，例如交接或子 Agent 调度；同一上下文中的内联调用不能达到这一效果。不要据此给普通写作任务强加委派。合并原本隔离的序列时，也要评估后续步骤是否破坏前一步完成。

完成条件应同时可检查并覆盖全部要求。保留原指令的输入、范围、适用条件、例外、恢复和授权边界；只改善表达不意味着改变政策。

## 引导词与直接表达

模型已有的紧凑概念可锚定行为，提示、文档和代码使用同一术语也能帮助抵达正确材料。用已知引导词收敛重复解释，重复词而非重复一整段含义。自造词需要定义，不能把“精简”变成让读者解码新行话；弱词无效时换成更准确的词，不堆解释。

优先描述应执行的正向动作。无法正向表达的硬性护栏保留禁止语句，并给出目标行为。不要为自然语气弱化必须、不得、仅当等约束。

## 删减与事实来源

一项含义保留一个事实来源，避免重复人为放大其权重。package.json 脚本、配置、目录和 `--help` 也是事实来源；一文件或一命令能查到的信息留在环境中。保留环境无法表达的未成文约定、决策原因和易错边界。

逐行判断是否影响当前任务，移除纯背景、过期事实，将条件分支放回它的披露层级。依据真实运行判断哪些指令没有改变默认行为；无效时整句删除，不只修短措辞。不要凭直觉认定关键要求是常识而删掉。

## 核对指令

对照修改前后文本，核对每个独立触发、动作、完成条件与例外。用适用和相邻但不适用的任务检查指针；区分文本推演与真实执行证据。编写 Skill 时，还需按入口读取 Skill 机制，核对 description、正文及宿主元数据一致。
